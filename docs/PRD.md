## 1. 产品概述

### 1.1 产品定位

Factory Bridge 是一款部署在工厂边缘侧（工控机/边缘服务器）的 **IIoT 边缘网关平台**，负责：

> 南向连接异构工业设备（PLC / 变频器 / 机器人 / 暖通冷机 / 电力远动装置）→ 毫秒级采集调度 → 边缘数据清洗与标度变换 → 本地时序存储 → 北向云端上报与边缘联动控制。

Web 控制台是本产品的运维与配置界面，同时提供实时监控、在线诊断与历史分析能力。

### 1.2 目标用户与核心场景

| 用户 | 场景 | 高频功能 |
|---|---|---|
| 现场调试工程师 | 项目交付期：接线后逐台设备接入、点位标定、联调 | 设备管理、参数诊断、报文诊断 |
| 产线运维人员 | 日常运行：看板巡检、异常追查、工艺参数核对 | Dashboard、Historian、告警 |
| 工艺/自动化工程师 | 换线与工艺优化：配方切换、联动逻辑编写 | 配方管理、边缘脚本（JS） |
| IT/系统集成商 | 系统对接：数据库、MQTT、WebAPI 集成 | 系统配置 |

### 1.3 产品目标（可量化）

- 单网关支持 **≥ 8 种工业协议**、**≥ 100 台设备**、**≥ 10,000 点位**并发采集。
- 最快采集周期 **≤ 100ms**；端到端（设备 → 界面显示）延迟 **≤ 1s**。
- 时序数据本地写入 **≥ 10 万点/秒**（依赖 TDengine），历史查询 24h 窗口响应 **≤ 3s**。
- 断网续传：网络中断恢复后，缓存数据 **零丢失** 按序补传。

### 1.4 名词表

| 术语 | 含义 |
|---|---|
| 通道（Channel/Bridge Node） | 一个南向连接实例，对应一台设备或一个 PLC 连接 |
| 位号（Tag / 点位） | 最小数据单元，含变量名、地址、类型、单位、标定 |
| 标度变换（Scaling） | 原始值 × scale + offset 转工程量 |
| 读计划（Read Plan） | 相邻地址合并为一次批量报文读取的调度单元 |
| STable | TDengine 超级表，一类设备一张超级表、每设备一张子表 |
| 设备影子 | 边缘侧维护的设备最新状态 JSON 快照（期望值 vs 上报值） |
| Reliable Outbox | 断网时本地缓存遥测、恢复后按序补传的机制 |

## 2. 系统边界与总体架构

### 2.1 系统组成

原型仅覆盖 **Web 控制台 UI**。实际系统由三部分组成：

```
┌─────────────────────────────────────────────────┐
│  Web 控制台（本原型已覆盖）                        │
│  React + TS SPA，通过 REST + WebSocket 访问网关    │
└───────────────────┬─────────────────────────────┘
                    │ REST（配置/查询） + WS（实时推送）
┌───────────────────┴─────────────────────────────┐
│  网关运行时（待开发，本 PRD 重点）                  │
│  ├─ 南向采集引擎（多协议驱动）                      │
│  ├─ 采集调度器（时间片/读计划聚合）                  │
│  ├─ 数据处理管道（清洗/标度/死区）                   │
│  ├─ 存储引擎适配（TDengine/PostgreSQL/SQLite）     │
│  ├─ 北向上报（MQTT/Sparkplug B、Outbox、影子）     │
│  ├─ 边缘脚本引擎（JS 沙箱）                        │
│  └─ 配置中心（持久化配置、变更热生效）               │
└─────────────────────────────────────────────────┘
```

### 2.2 已确认的技术决策（2026-09-06 评审）

| 决策项 | 结论 |
|---|---|
| 网关运行时技术路线 | **Node.js / TypeScript 全栈**（与前端同语言；驱动库：`modbus-serial`、`node-snap7`、`node-opcua`） |
| MVP 首发协议 | **Modbus TCP + Siemens S7 + OPC UA**（其余协议 Phase 2/3） |
| 界面语言 | **中文优先，第一版接入 i18n 框架**，原型英文文案作为英文语言包复用 |
| 部署基线 | **Linux + Windows 双支持**（选型库须双平台验证，见 §11） |

工程组织建议采用 pnpm monorepo：

```
iotconnector/
├─ apps/
│  ├─ console/      # Web 控制台（当前原型演进，React 19 + Vite + Tailwind）
│  └─ gateway/      # 网关运行时（Fastify + WS；采集引擎/调度器/存储管道/北向上报）
├─ packages/
│  └─ shared/       # 共享类型与协议常量（Tag/Channel 模型、协议参数 schema 单一来源）
└─ docs/
```

- 控制台与网关同机部署（单机版）优先，通过 REST + WebSocket 通信；架构预留远程多网关管理。
- `packages/shared` 中的协议参数 schema 同时驱动：后端参数校验、前端动态表单渲染、配置导入导出校验（一份 schema 三处使用）。

## 10. 核心数据模型（草案）

```
Channel（通道）
  id, name*, protocol, host, port, enabled, params(JSON, 按协议),
  status, lastError, createdAt, updatedAt

Tag（位号）
  id, channelId→Channel, name*(通道内唯一), address, dataType,
  unit, scale, offset, engMin?, engMax?,
  deadband?, accessMode(RO/RW), description
  —— 运行态：value, quality, timestamp（引擎内存/Redis，不入库）

AlarmRule（告警规则）
  id, tagId, type(Limit/Deviation/RateOfChange), level,
  threshold..., enabled, hysteresis

AlarmEvent（告警事件）
  id, ruleId, state(Active/Acked/Cleared), value, message, timestamps

StorageTask（存储任务）
  id, name, enabled, target(STable/表名), trigger(cycle/deadband/edge/expression...),
  batchTagId?, mappings[{column, tagId}]

Recipe（配方）
  id, name, description, enabled, version,
  items[{tagId, value}], 下发记录单独成表

Script（脚本）
  id, name, description, code, trigger(tagEdge/expression/period), enabled,
  运行统计单独成表

SystemConfig（系统配置，单例 JSON 分节）
  db / mqtt / redis / webapi / gateway / security

User / Role / AuditLog（跨模块）
```

> 关键设计原则：**一个位号模型贯穿全系统**（设备管理配置它、引擎采集它、看板展示它、Historian 查询它、脚本读写它）。原型中 `data.ts::Tag` 与 `DeviceManagement::TagMapping` 两套模型必须合并。
